## The auto-crosswalk claim: RESOLVED by building it (and one correction)

### Correction to the earlier version of this finding

A previous pass of this log stated that no propagation logic existed "across
both repositories." That was true of ControlWeaver-Pro and **wrong about
ai-grc-platform**. I searched this repository, found nothing, and generalized
to the mirror without checking it. ai-grc-platform has had automatic
propagation all along: `PUT /controls/:id/implementation` credits mapped
controls when a control becomes `implemented`, at an org-configurable threshold
(`crosswalk.inheritance_min_similarity`, default 90) restricted to strict
mapping types, and `POST /controls/:id/inherit` does the same on demand. Its
`README.md` and `PROJECT_STATUS.md` claims were accurate; they were never the
problem.

What was true of both repositories is narrower: **credit was never withdrawn,
and never explained.**

### The finding that stands

In ControlWeaver-Pro, `qa:crosswalk:live` defaults to the production Railway
URL, so it had never run against a local build; against production it fails at
login and never reports. Pointed at localhost it produced a real result: the
mapped control did not transition to `satisfied_via_crosswalk`. No JavaScript
set the status outside seed scripts and the manual allowlist in
`routes/implementations.js`; there were no triggers on
`control_implementations`, no stored function mentioning the status, and no
migration referencing it. The behavior was documented and unbuilt.

In ai-grc-platform the forward path worked, but un-implementing a source left
every control it had satisfied credited forever — the organization kept a
compliance posture it no longer had — and the only trace of *why* a control was
satisfied was a sentence appended to a free-text notes column.

### The decision: build it

Chosen over correcting the claim, because the claim describes the product's
flagship differentiator and the gap was in the mechanism, not the pitch.

**ControlWeaver-Pro** — built from scratch: migration `132`
(`control_crosswalk_credits`), `services/crosswalkPropagationService.js`, hooks
in `routes/controls.js` and `routes/implementations.js`, provenance on
`GET /controls/:id`, AU-2 audit logging, and a 12-case Jest suite.

**ai-grc-platform** — the existing forward propagation was left in place (it
carries evidence-link propagation and a configurable threshold that a wholesale
replacement would have regressed) and extended: migration `138` adds the same
ledger, `services/crosswalkCreditService.js` records provenance and performs
withdrawal, and both `PUT /controls/:id/implementation` and
`PATCH /implementations/:id/status` now withdraw credit when a source leaves
`implemented`/`verified`. 14-case Jest suite.

One behavior change in ai-grc-platform worth flagging on its own: crediting is
now restricted to frameworks the organization has activated. Crediting controls
in unadopted frameworks inflated the compliance percentage the dashboard
reports. Organizations with no `organization_frameworks` rows have declared no
scope, so the previous unrestricted behavior still applies to them — 6 of 26
organizations in the live database are in that state.

### Verified live, through the HTTP routes

Not through reconstructed SQL — through `PUT /controls/:id/implementation` and
`GET /controls/:id` against a running server and the seeded demo database, for
Meridian Financial Group (`sr_11_7` SR117-G-3 → `nist_ai_rmf` GOVERN-6 @ 92%):

- credit applied, target moved `not_started` → `satisfied_via_crosswalk`
- `GET /controls/:id` returned the provenance: source framework, control ref,
  similarity, mapping type, and the source's current status
- source moved to `needs_review` → credit withdrawn, target back to
  `not_started`
- multi-source (GOVERN-1, credited by SEC-AI-5 @ 90% and SR117-G-1 @ 95%):
  stayed satisfied when the first source lapsed, restored only when the second
  did
- a target a human had moved to `in_progress` was neither overwritten nor
  recorded in the ledger

## Out of scope, noted not fixed

- **`docs/TIER_COMPARISON.md`** and the "Feature Availability" section of
  `USER_GUIDE.md` still frame the product in terms of the removed tier system.
  That is deliberate historical context per `.claude/rules/tier-system.md`, and
  predates this PR.
- **`docs/guides/` has no index listing available guides.** Pre-existing
  structural gap; the `USER_GUIDE.md` navigation is the de facto index, which
  is why finding 2 mattered.
- **`src/routes/publicContact.js` has a rate limiter here but not in the
  `ai-grc-platform` mirror**, and the endpoint is unauthenticated in both.
  Pre-existing divergence, unrelated to this diff, worth its own change.
- **`TRUST_PROXY` is undocumented and unset, which may silently collapse every
  rate limit into one global bucket.** `server.js` does
  `app.set('trust proxy', process.env.TRUST_PROXY === 'true' ? 1 : process.env.TRUST_PROXY)`,
  so with the variable unset the value is `undefined` — falsy — and Express
  resolves `req.ip` to the socket peer. Behind Railway's edge that is the
  proxy's address for *every* request. Since `createRateLimiter`'s default key
  generator is `req.ip`, all clients would then share a single bucket for every
  limit in the app, and `audit_logs.ip_address` would record the proxy rather
  than the caller. Most likely `TRUST_PROXY` *is* set in the Railway
  environment — otherwise the deployed app would be constantly 429-ing on the
  5/min bulk-upload limit — but nothing in the repo said so. Documented it in
  `backend/.env.example` (both repos) rather than changing the global proxy
  trust default, which is a deployment-security decision rather than a code
  fix. **Worth confirming against the deployed environment.**

  Noting explicitly that this is pre-existing and was not made worse by this
  PR: the router-level bounds added here (2000/15min ≈ 133/min) are far looser
  than limits this branch did not touch, such as `evidence-bulk-upload` at
  5/min, so they are never the binding constraint in either configuration.
- **Seven unlimited evidence routes — now FIXED in both repos.** Raised in an
  earlier pass as pre-existing and outside the diff; fixed on request.
  `GET /:id/download` and `GET /:id/integrity-check` at 30/min (the download
  path is the bulk-exfiltration route for files that may carry PII, and every
  org's evidence library is enumerable by id from the list endpoint;
  integrity-check re-hashes the stored file on each call), `DELETE /:id` at
  30/min (destructive and irreversible), `PUT /:id`, `POST /:id/link` and
  `DELETE /:evidenceId/unlink/:controlId` at 60/min, `GET /:id` at 120/min.
- **`scripts/seed-hf-demo-data.js` hard-fails the demo orchestrator when
  Hugging Face is unreachable.** Observed during live verification. It is the
  final step so everything before it succeeds, but a network outage makes
  `seed:demo:all-test-data` exit non-zero. Pre-existing.
- **Migration 128's RLS policies are inert when the app connects as a
  superuser**, because PostgreSQL always exempts `rolsuper`/`rolbypassrls` and
  `FORCE ROW LEVEL SECURITY` only removes the owner's exemption. Documented in
  the migration header, and `verify-rls-isolation.js` now tests the policies
  with a `NOSUPERUSER NOBYPASSRLS` probe role. Whether a given deployment's
  `DATABASE_URL` uses a non-superuser role is an infrastructure question.

## Conclusion

Two genuine gaps this pass, both fixed: a new AI analysis type missing from the
enumeration that is supposed to list them all, and the Access Governance guide
being unreachable from the user guide's navigation. The demo-credential docs
were rewritten as part of the diff itself. `AI_COPILOT.md` and
`ACCESS_GOVERNANCE.md` were re-read against the code and are accurate as
written — including the self-review and SoD-default caveats, which are the
statements most likely to be challenged in an assessment.

The largest item this pass was the auto-crosswalk claim, closed by building the
engine rather than softening the documentation — and by correcting this log's
own earlier overreach, which condemned both repositories on evidence gathered
from only one. The docs describing the forward behavior in ai-grc-platform were
right the whole time; what neither repository could do, and both now can, is
explain a credit and take it back.
