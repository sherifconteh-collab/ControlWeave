## Findings

### 1. `.claude/rules/evidence.md` taught the pre-migration isolation model — fixed

The rule's Evidence-Control Linking example joined `evidence_control_links` and
then filtered on `e.organization_id`, because until migration `144` the junction
table had no tenant column to filter on. That query is still correct, but it
described isolation as a property each query had to remember rather than one the
schema enforces, and it was the only guidance a future change would have read.

Updated to filter `ecl.organization_id` directly, to state why the column exists,
and to show the insert form the eleven call sites in this PR now use — taking
`organization_id` from the `evidence` row rather than from `req.user`, so a link
cannot be filed against a different tenant than the document it points at.

### 2. `guides/EVIDENCE.md` needed no change — and that is the right outcome

Steps 4.1–4.3 describe linking and unlinking evidence from the UI. Migration
`144` adds a column and changes no request, response, permission or screen, so
the guide describing the user-facing flow stays accurate as written. Checked
rather than assumed: the linking endpoints' request bodies and responses are
unchanged in `openapi.yaml`, and the migration backfills from
`evidence.organization_id`, so no existing link is dropped or reassigned.

Recording this explicitly because a review that only reports problems is not
trustworthy. This one is genuinely fine.

### 3. `guides/AUDITOR_WORKSPACE.md` — unaffected, and worth saying why

This PR changes 140 lines of `dashboard/auditor-workspace/page.tsx`, which looks
like it should move the guide. It does not: every change is a type annotation
replacing `any`, with no change to what renders or what the page requests. The
one behavior fix in that file — an unguarded `agent.durationMs / 1000` rendering
a literal `NaNs` — shipped in #691 and is already recorded in its release notes.

### 4. `openapi.yaml` was sixteen paths behind the API — fixed

The document described 13 paths. The risk, CMDB, evidence and POA&M endpoints
added across migrations `140`–`143` were absent, including every reverse read
(`GET /evidence/:id/risks`, `GET /cmdb/assets/:assetId/risks`,
`GET /cmdb/risk-exposure`). Now 29. The `relevance` enum, the
`requires_poam_submission` 400 contract, and the export format parameter are
described rather than left for a reader to infer from the route files.

### 5. The IP hygiene check failed on prose no PR had touched — fixed

Not a documentation discrepancy, but it is what kept this PR red, and its cause
is documentation, so it belongs in this log.

`Backend — Syntax & IP Hygiene` and `QA Testing Suite` both failed on two lines
of `controlweave/docs/RELEASE_NOTES.md`. Neither line is in this PR's diff:
the release automation generated them on `main` in `7ad1607` under `[skip ci]`,
so no run on `main` had ever exercised them, and this PR was the first build to
include the file.

The check itself was wrong. Rule 3 tested a line against a quote character,
120-plus characters of anything, then the same quote character — measuring the
distance from a line's first quotation mark to any later one rather than the
length of a quotation. A sentence naming several terms of art fired it, and so
did two ordinary possessive apostrophes. Both flagged lines were original prose:
one lists what each framework calls a corrective action, the other quotes our own
404 message.

The script advertises an `ip-hygiene:ignore` marker for exactly this, and using
it would have been one line. It was the wrong fix — the next generated release
note quoting two short strings would fail the same way, and the marker would have
recorded original prose as licensed standards text. Delimiters are now paired in
order of appearance, and an apostrophe glued to word characters on both sides is
treated as punctuation. Verbatim standards text of the length the rule was
written to catch still flags, including a quotation containing an internal
apostrophe; the mirror repository's three genuine flags, all long framework
descriptions in its seed SQL, are untouched.

### 6. The pipeline flagged three feature areas as `ui-change` — none of them are

`detect-feature-changes.js` classified this diff as a UI change to controls,
evidence and integrations, queueing eleven doc files including `CONTROLS.md`,
`INTEGRATIONS.md`, `SPLUNK.md`, `WEBHOOKS.md`, `SSO.md`, `OLLAMA.md`,
`API_DOCS.md` and `USER_GUIDE.md`. Each flagged file was checked against the
actual diff.

Every change in `controls.js`, `github.js`, `splunk.js`,
`autoEvidenceCollection.js`, `pendingEvidence.js`, `organizations/_helpers.js`
and `jobService.js` is the same edit: an `INSERT INTO evidence_control_links`
gains an `organization_id` column, and a `VALUES` clause becomes a
`SELECT ... FROM evidence e WHERE e.id = $1` so the value comes from the
document's own row. No route, request body, response, permission or screen
changes. None of the eleven files needs an edit, and none received one.

The detector keys on which route files a diff touches, not on what changed in
them, so a schema-only change to a route file reads as a UI change to that
feature. Worth knowing before treating a queued comment as evidence that a doc
is stale — it is a prompt to look, not a finding.

The same comment reports screenshots skipped for absent `DEMO_USERNAME` /
`DEMO_PASSWORD`, with a pointer to the `workflow_dispatch` capture job that
needs no secrets. That is the honest-skip behavior #691 built to replace a step
that failed on every run; working as designed, no action.
